## 결론 먼저

**상태** : 설계 끝, 구현 전. 사용자에게 물을 것은 둘이다(옛 Laya 자리 치우기 · GitHub 저장소 자리, 끝 절).

**판정 사다리 (mem 쪽에서 본 꼴)**

```
① 규칙 rules-v1 (Go, 1ms)            걸리면 끝 (mem judge 는 B·C, retain 은 B 만)
      ↓ 안 걸림
② NLI nli-v1 (JudgeModel 서버, 0.2~0.5초) 확신이면 끝 — 지지는 nli_sure_support, 반대·무관은 nli_sure 이상
      ↓ 확신 없음 · 서버 없음
③ SemIf support-v3 (LLM 서버 있을 때)   답하면 끝
      ↓ 서버 없음
④ 보류 (Unsure)
```

- 앞 설계의 「규칙 → Laya → SemIf → 보류」에서 ② 자리만 바뀐다. **Laya 는 모델·학습 코드를 버리고** HTTP 꼴(`{"a","b","c","model","ms"}`)과 Go 호출 자리만 물려받는다.
- **JudgeModel 이 학습 · 측정 · 서빙(HTTP)을 다 갖는다.** AIMemoryTool 에는 Go HTTP 손님만 남고, JudgeModel 을 경로로 가리키지 않는다(설정 URL + 「JudgeModel 응답 꼴을 따른다」 글로만).
- **세 자리로 나눈다** (10-05 인수인계 구도) : 공개될 JudgeModel 저장소 = 코드 + 공개 NLI 로만 가르친 **기본 모델** `nli-base-v1` · 스튜디오 = mem 쌍으로 덧학습한 **스튜디오 모델** `nli-studio-v1`(비공개, git 밖) · 게임 저장소 = 기본 모델에서 자기 기억으로 다시 맞춤(이번 판 밖).
- 새 이름 : 단 `nli` · 판 `nli-v1` · 설정 `nli_url` · `nli_timeout_ms` · `nli_sure` · `nli_sure_support`.
- **학습은 한 스크립트가 `--device cuda|cpu` 만 바꿔 돈다.** 1순위 미니PC GPU(다른 툴에서 쓰던 podman 이미지 — 이름만 씀), 2순위 미니PC CPU.
- **게임 서버가 지금 내려가 있어**(사용자 10-09) GPU 벤치를 첫 작업으로 당긴다. 처음 띄우는 판은 사람이 있을 때 · 스왑이 늘면 바로 내림 · 미니PC 설정 안 바꿈은 그대로다.

## 1. 0단계 — ko-decision 무학습 측정 (넣는다)

**정한 것 : 넣는다. 다만 K 48 에서만, 2시간 상한, 「서빙하려는」 것이 아니라 「출발점을 고르는」 관문으로 쓴다.**

| 항목 | 내용 |
| --- | --- |
| 무엇 | `mmetamong/ko-decision-roberta-large-klue` 를 받아 학습 없이 K 48 에 한 번 잰다 |
| 어디서 | N1 벤치가 통과하면 미니PC GPU(추론만, 몇 분), 아니면 미니PC CPU(`~/judge-laya/.venv` 의 torch cpu — 설치 0, 피크는 large 학습 벤치 10.4GB 아래) |
| 꼴 | 카드가 적은 「선택지마다 점수」 꼴 그대로. 한 번 쓰는 평가 스크립트 `train/kodecision_eval.py` (서빙에 안 들어간다) |
| 상한 | 내려받기부터 결과까지 **2시간**. 넘으면 버리고 본 길로 간다. 이 단계는 본 길을 막지 않는다 |
| 함께 볼 것 | `config.json` 의 `architectures` — 표준 `RobertaModel` 인코더를 떼어 쓸 수 있는가 |

**갈림 (미리 못 박음)**

| K 48 결과 | 다음 |
| --- | --- |
| 정확도 ≥ 41/48 · 반대 ≥ 12/16 · 거짓 지지 ≤ 3 **이고** 인코더를 뗄 수 있음 | **지름길** : ko-decision 의 **인코더만** 시작점으로 쓰고 3갈래 머리를 새로 붙인다. 기반 학습은 KLUE-NLI 1 바퀴(머리 맞추기)로 줄이고 KorNLI 는 건너뛴다 → N7 |
| 그 밖 | 본 길 : `klue/roberta-large` 에서 기반 학습(2절·3절). ko-decision 수치는 견줌 한 줄로만 남긴다 |

왜 :
- ko-decision 은 KLUE-NLI 90.7% 라 **「잘 배운 한국어 NLI 가 우리 쌍에서 얼마나 하나」** 를 학습 없이 미리 보여 준다. 우리 기반 학습이 닿을 자리(KLUE 89.5)와 비슷해서, 중립↔무관 · 함의↔지지 뜻 차이가 얼마나 큰지 금방 안다.
- 조사의 「선택지마다 3번 계산 → p95 1초 위험」은 **서빙하지 않으면 사라진다.** 지름길이어도 인코더만 가져와 한 번 계산 꼴로 바꾸므로 서버 꼴은 하나로 남는다.
- K 48 은 이미 여러 번 쓴 견줌 셋이라 여기서 써도 game90 의 「한 번만」을 깨지 않는다. game90 은 0단계에 안 쓴다.
- 라이선스는 둘 다 CC BY-SA 4.0 이라 갈림에 따라 기본 모델의 공개 조건이 달라지지 않는다. 다만 지름길이면 `model.json` 의 출처에 ko-decision 을 적는다.

## 2. 자료 섞기

### 2-1. 첫 단계 : 토큰 길이 재기 (N4)

모델을 받으면 **학습 전에** `train/data_prep.py --measure` 로 klue 토크나이저 실제 토큰 수를 잰다. 어림(1토큰 ≈ 1.5~2자)을 쓰지 않는다.

| 잴 셋 | 쓰는 곳 |
| --- | --- |
| KLUE-NLI 학습 · KorNLI 표본 1만 | 기반 학습 `max_len` |
| mem train+dev 1,330 · K 48 · (game90 은 길이만, 라벨 안 봄) | 덧학습·서빙 `max_len` |

**`max_len` 고르는 규칙** (잰 값으로 기계적으로)

- 후보 `{128, 192, 256, 320}` 중 **그 셋의 95% 이상을 자르지 않는 가장 작은 값**. 320 위로는 안 간다(메인 PC p95 1초 자).
- 기반 학습은 128, 덧학습·서빙은 256 이 될 것으로 본다(조사 : 글자 p95 560).
- **자르는 쪽은 근거만**(`only_first`). 주장은 최대 121자라 안 잘린다. 근거는 앞부분을 남긴다 — 「long」 갈래의 요약은 본문 앞쪽에 있는 일이 많다.
- 잘린 쌍 수를 `train_info.json` 에 적는다.

### 2-2. 기반 학습 자료 (= 공개 기본 모델의 자료)

| 자료 | 몫 | 까닭 |
| --- | --- | --- |
| KLUE-NLI 학습 | **24,998 전부** · 바퀴마다 다 씀 | 사람이 쓴 한국어 · 번역체 아님 |
| KorNLI 학습 | **바퀴마다 새 표본 2만 5천** (2 바퀴 = 5만, 겹침 없음) | 기계 조사 3절 : CPU 로 「KLUE + 5만」이 밤 한 판 |
| 그 안 비율 | MNLI 70% · SNLI 30% | MNLI 는 여러 갈래 글(우리 기술 문장에 가깝다), SNLI 는 그림 설명 문장 |
| 라벨 균형 | KorNLI 표본은 세 라벨 1/3 씩. KLUE 는 원래 거의 균등이라 그대로 | 반대가 모자란 것이 Laya 의 뿌리 문제였다 |
| 번역체 비율 | 한 바퀴 5만 쌍 중 **50%** | 조사 7절 「번역체」 — KLUE 몫을 반 아래로 안 내린다 |
| KorNLI dev/test · XNLI · ANLI | **안 씀** | 비상업(NC). 쓰면 기본 모델을 공개 못 한다 |

- **GPU 길이고 N1 벤치가 분당 1,500쌍 이상이면** KorNLI 를 바퀴마다 5만(2 바퀴 10만)으로 늘린다. 번역체 비율은 67% 가 된다 — 이것이 상한이다. 이 갈림은 벤치 숫자로만 정하고 결과를 보고 바꾸지 않는다.
- 표본 씨앗 1 · 뽑힌 행 번호 목록을 `data/prep/kornli-sample-<seed>.txt` 로 남긴다(같은 판 다시 만들기).
- 한 바퀴 안에서 KLUE · KorNLI 를 **섞어서** 돈다(이어서 돌리면 실물 모순 재현이 떨어졌다는 보고, 조사 4절).

### 2-3. 라벨 매핑 표

모델 출력 칸 차례를 **처음부터 a·b·c 로** 둔다. 그러면 서버·Go 쪽에 바꿔 끼우기가 없다.

| 출력 칸 | 뜻 | KLUE-NLI 라벨 id | KorNLI 글 | mem 쌍 `want` |
| --- | --- | --- | --- | --- |
| 0 | A 지지 (`a`) | 0 entailment | entailment | support |
| 1 | B 반대 (`b`) | 2 contradiction | contradiction | contradict |
| 2 | C 무관 (`c`) | 1 neutral | neutral | unrelated |

- 바꿔 끼우기는 `data_prep.py` 한 곳에서만 한다. `model.json` 에 갈래 차례와 원본 매핑을 적는다.
- KLUE 라벨 -1(라벨 없음)이 있으면 버리고 수를 적는다.

## 3. 학습 고리 (`train/train_nli.py`)

**datasets · accelerate 없이 torch 순수 고리.** 이미지에 없는 것을 안 깐다. 기반 학습과 덧학습이 같은 스크립트다(`--init` 과 자료만 다르다).

### 3-1. 뼈대

| 함수 | 하는 일 |
| --- | --- |
| `load_jsonl(path)` | `{premise, hypothesis, label(0~2), src}` 줄을 읽는다 (mem 쌍은 `evidence→premise`, `claim→hypothesis`) |
| `make_batches(rows, tokenizer, max_len, batch, seed, epoch)` | 길이별 묶음 패딩. 씨앗·바퀴로 차례가 정해져 **재개 때 같은 차례**가 나온다 |
| `build_model(init, device, dtype)` | `AutoModelForSequenceClassification(num_labels=3)` · 지름길이면 `ignore_mismatched_sizes` 로 머리만 새로 |
| `train_step(model, batch, optimizer, scheduler, class_weight)` | 전진·역전파·기울기 자르기 1.0 |
| `evaluate(model, rows)` | 정확도 · 갈래별 재현 · 거짓 지지 · 혼동표 · 평균 손실 |
| `save_checkpoint(dir, state)` / `load_checkpoint(dir)` | 모델 · 옵티마이저 · 스케줄러 · RNG · 바퀴·스텝 위치 |
| `write_heartbeat(path, step, loss)` | 스텝마다 시각·스텝·손실을 덮어 쓴다 (감시용) |
| `main()` | 인자 : `--device cuda|cpu` · `--dtype bf16|fp32` · `--init` · `--train` 여러 개 · `--dev` · `--out` · `--resume` · `--smoke` · `--threads` |

### 3-2. 하이퍼파라미터 (권장 값, 바꾸면 `train_info.json` 에 남는다)

| 값 | 기반 학습 | 덧학습 |
| --- | --- | --- |
| lr | 1e-5 (머리도 같은 값) | 1e-5 |
| 바퀴 | 2 | 최대 4 (바퀴마다 dev, 가장 좋은 바퀴 고름) |
| batch | 32 (CPU 는 16 × 누적 2) | 16 |
| warmup | 전체 스텝의 6% → 선형 감소 | 10% → 선형 감소 |
| AdamW | wd 0.01 · eps 1e-6 · betas (0.9, 0.98) | 같음 |
| 정밀도 | GPU : N1 벤치가 통과하면 **bf16 autocast**(가중치·옵티마이저는 fp32), 아니면 fp32 · CPU : fp32 | 같음 |
| 씨앗 | 1 | 1 |
| 검증 | KLUE-NLI dev 3,000 · 2,000 스텝마다 + 바퀴 끝 | 새 dev (4절) · 바퀴 끝 |
| 고르는 기준 | KLUE dev 정확도 최고 | 4-2 |

- **roberta-large 무너짐 막기** : large 는 가끔 한 라벨만 내는 쪽으로 무너진다. 2,000 스텝에 KLUE dev 정확도 < 0.50 이면 멈추고 씨앗 +1 로 다시 시작한다(최대 2번). 세 번 다 무너지면 lr 5e-6 으로 한 번.
- GPU 에는 `TORCH_ROCM_AOTRITON_ENABLE_EXPERIMENTAL` 을 N1 벤치 결과대로 켜거나 끈다.

### 3-3. 멈춤 조건 · 감시

학습은 감싸개(`run/cpu-train.sh` · `run/podman-train.sh`)가 띄우고, 감싸개 안의 감시 고리가 10초마다 본다.

| 조건 | 처리 |
| --- | --- |
| 심장 박동 파일이 **60초** 넘게 안 바뀜 | 프로세스를 죽이고 `stop_reason: "stall"`. GPU 가 멎어 죽지도 않으면 사람에게 알리는 줄만 남긴다(재부팅은 사람 몫) |
| 손실 NaN·inf 3 스텝 연속 | 마지막 검사점에서 멈춤 · `stop_reason: "nan"` |
| 게임 서버가 떠 있는데 MemAvailable < 10GB | 검사점 저장 뒤 멈춤 · `stop_reason: "memory"` |
| 스왑 사용이 시작 때보다 256MB 넘게 늚 | 같음 · `stop_reason: "swap"` (게임 서버가 없어도 — 「스왑 늘면 바로 내림」) |
| 정상 끝 | `stop_reason: "done"` |

- **메모리 상한** : CPU 길은 지금처럼 `systemd-run --user --scope -p MemoryMax=12G -p MemorySwapMax=0 nice -n 19`. GPU 길은 메모리가 GTT 에서 나가 cgroup 이 못 잡으므로 위 감시가 상한 노릇을 한다.
- **게임 서버가 학습 중에 다시 뜨면** : GPU 판은 게임 서버와 같이 돈 실측이 없다. 감시 고리가 10초마다 게임 서버 프로세스도 보고, 뜨면 검사점 저장 뒤 멈춘다(`stop_reason: "gameserver"`). 그 판의 메모리 실측으로 공존 여부를 정하기 전까지 이렇게 둔다.
- **재개** : 검사점은 1,000 스텝 또는 20분마다 `ckpt-last/` 에 덮어 쓰고, dev 최고는 `ckpt-best/` 에 둔다. `--resume` 은 `ckpt-last/` 의 바퀴·스텝 위치부터 같은 차례로 잇는다.
- **`--smoke`** : 64쌍 · 8 스텝 · CPU. 스크립트가 끝까지 도는지(저장·재개·평가·기록 파일)만 본다.

## 4. 덧학습 (mem 실물 쌍 → 스튜디오 모델)

**이 단계부터는 스튜디오 몫이다.** 결과 모델 `nli-studio-v1` 과 자료는 git 밖에만 두고 JudgeModel 저장소에 안 들어간다(mem 저장소 자료 반출 금지).

### 4-1. dev 다시 가르기 (`train/split_pairs.py`)

조사 2절 : dev 기억 131개 중 115개가 train 에도 나와 dev 가 낙관이다. **기억 단위로 다시 가른다.** 스크립트는 「쌍 jsonl 의 `src_ids` 로 덩이를 만든다」는 일반 꼴이라 mem 경로를 모른다(입력·출력 경로는 인자).

1. 풀 = 앞 mem 저장소(비공개) `local/laya2/train.jsonl` 1,230 + `dev.jsonl` 100 = 1,330쌍.
2. 쌍의 `src_ids` 를 이어 **덩이**를 만든다 — 기억 하나라도 같이 쓰는 쌍은 한 덩이(합집합 찾기).
3. 덩이 단위로 섞어 **dev 약 15%(≈ 200쌍)** 를 뽑는다. 갈래(`want`)별 dev 몫이 13~17% 안에 들 때까지 씨앗 1부터 다시 뽑는다. 반대 dev 는 40쌍 이상.
4. 검사 : train ∩ dev 기억 id **0**. `kind` 별 수(flip · rewrite · supersede …)를 `MANIFEST.txt` 에 적는다.
5. 출력 mem 저장소(비공개) `local/nli1/{train,dev}.jsonl` · `MANIFEST.txt`(SHA · 수 · 씨앗). 앞 `laya2/` 는 읽기만 한다.

덩이 하나가 풀의 15% 를 넘어 못 가르면 그 덩이는 train 에 두고 수를 적는다.

### 4-2. 섞기 · 치우침

| 정한 것 | 내용 | 까닭 |
| --- | --- | --- |
| 시작점 | `nli-base-v1` 의 `ckpt-best` | 공개 기본 모델 위에 얹는다 — 게임 저장소도 같은 기본 모델에서 시작하게 |
| 잊음 막기 | 바퀴마다 mem train 전부 + **같은 수의 KLUE-NLI 무작위 쌍**(1:1) | 1,100여 쌍만 돌면 NLI 에서 배운 반대를 잊는다 (조사 7절 「실물 반대 부족」) |
| 치우침 | **갈래 가중치**(손실 가중) — mem 쌍에만, 갈래 수의 역수를 평균 1 로 맞춤. KLUE 쌍은 가중 1 | 겹쳐 뽑으면 합성 반대(flip·rewrite)가 두세 번 들어가 앞 실측의 「합성 쏠림」이 커진다. 가중치는 쌍을 늘리지 않는다 |
| 고르는 기준 | dev 에서 ① 거짓 지지가 가장 적은 바퀴 중 ② 갈래 재현 최저값이 가장 높은 바퀴 | 앞 판이 가장 못 맞춘 것이 거짓 지지 · 반대였다 |

### 4-3. 중립 ↔ 무관 · 함의 ↔ 지지 뜻 차이

우리 판정 기준(`support-v3`)은 **「일부만 받쳐도 지지」 · 「어느 부분도 안 다루면 무관」** 이다. NLI 와 이렇게 어긋난다.

| NLI | 우리 | 어긋남 |
| --- | --- | --- |
| 함의 (반드시 참) | 지지 | 우리 지지가 더 넓다 — 요약 · 반올림 · 일부만 받침 · 링크 문장 |
| 중립 (같은 장면, 참·거짓 모름) | 대부분 **지지(일부 받침)** 또는 무관 | NLI 중립 안에 「일부 받침」이 섞여 있다 |
| 모순 | 반대 | 거의 같다 |

**정한 것 : 기반 학습은 중립 → C 로 그대로 두고, 뜻 차이는 덧학습이 메운다.** 기반 자료의 중립을 다시 라벨링할 방법이 없고, 우리 C 의 대부분(sscope·xscope 428/475)은 주제가 다른 쌍이라 NLI 중립보다 쉽다.
대신 덧학습 dev 에서 **지지 갈래를 `kind` 별로**(same · long · link · num) 따로 센다. long · link 지지 재현이 0.70 아래면 「뜻 차이 못 메움」으로 보고 replay 비를 1:1 → 2:1(mem 쪽 두 배)로 한 번만 바꿔 다시 돈다. 이 갈림도 dev 로만 정한다.

### 4-4. 온도 · 문턱 (`train/calibrate.py`)

- **온도 T** : 고른 바퀴의 dev 로짓에서 NLL 이 가장 작은 T 를 0.5~3.0 · 0.05 간격으로 찾는다. 결과는 `calibration.json` `{temperature, fitted_on(dev sha), nll_before, nll_after, ece_before, ece_after}`.
- 기본 모델도 KLUE dev 로 같은 셈을 해 자기 `calibration.json` 을 갖는다(게임 저장소가 그대로 쓸 수 있게).
- 문턱 고르기는 7절. 온도와 문턱 모두 **dev 로만** 정한다.

- 끝점 · 응답 · 127.0.0.1 · 한 번에 한 판(lock) · 1MB 상한 · 400/413/404 는 **옛 Laya 서버 그대로**. `GET /health` 는 `{"ok","model","backend","name"}`.

- 메인 PC 는 그때 있던 옛 서빙 venv `~/.laya-local/venv-serve`(onnxruntime · tokenizers · numpy)로 띄웠다 — 지금은 `venv-serve` 를 새로 만든다(README 「까는 법」).

### 6-2. 차례

1. **N9 game90 얼리기 (사람)** : 사람 확인 17건(덮음 14 · link 3)을 끝내고 `FROZEN.sha256` 을 적는다. 저장소엔 SHA · 갈래 수만. **얼리기 전에는 game90 을 재지 않는다.**

3. **한 번에 세 표** (메인 PC · `mem judge support --file … --stage …`, 서버는 `nli-studio-v1`) :

| 표 | 셋 · `--stage` | 보는 것 |
| --- | --- | --- |
| ① 견줌 | K 48 · `nli` | 앞 판들(SemIf 42/48 · Laya 41/48)과 견줌 |
| ② 모델 | game90 · `nli` | **최고 확률 답 그대로**(Unsure 무시) → 정확도 · 갈래 재현 · 거짓 지지 |
| ③ 사다리 | game90 · `rules,nli` | 실제로 쓸 꼴 → 확신 답의 거짓 지지 · 보류 비율 · 단별 수 |

- ②와 ③은 같은 모델 확률에서 나온다(③ 은 규칙 단이 앞에 붙는 것만 다르다). 둘 다 같은 자리에서 한 번에 돌리고 결과를 본 뒤 다시 돌리지 않는다.

### 6-3. 세는 법 · 자

| 항목 | 셈 | 표 | 자 |
| --- | --- | --- | --- |
| 정확도 | 맞은 쌍 / 103 | ② | ≥ 0.85 |
| 반대 재현 | 정답 B 중 B 로 본 것 / 30 | ② | ≥ 0.75 |

- **다 통과해야 통과다.** ②의 정확도·반대는 문턱 없이 재므로 보류를 늘려 점수를 꾸밀 수 없다. 거짓 지지는 실제로 쓸 꼴(③)에서 잰다 — 「거짓 지지는 확신 문턱으로 맞출 일」(mem 기록).

| 정확도·반대·거짓 지지·보류 중 하나라도 미달 | **길 1 을 접는다.** `nli_url` 을 비우고 사다리는 「규칙 → SemIf → 보류」 그대로. 수치를 mem history 로 남긴다. JudgeModel 은 푸시하지 않는다 |
| 다시 열 때 (사용자 판단) | **새 blind 셋을 먼저 만든다**(game90 은 이미 썼다). 후보 : 반대 미달이면 웹조사 길 3(LLM 합성 반대 + 증류) · 정확도만 아깝게 미달이면 KorNLI 몫을 늘린 GPU 판. base 로 줄이기는 정확도 미달의 답이 아니다 |

**잰 뒤 문턱·바퀴·온도를 game90 결과를 보고 다시 고르지 않는다.**

## 7. 길 2 — 확신 문턱 · 보류 층

**사다리** : 규칙 → NLI(확신이면 확정) → SemIf(`url` 이 있을 때) → 보류. Go 흐름은 지금 `Judge.Support` 그대로이고 Unsure 판정만 바뀐다.

```
NLI 답이 Unsure 인 때 =
    두 갈래 차가 tieGap 아래 (지금 unsureOf)
 또는 답이 A 이고 확률 < nli_sure_support
 또는 답이 B·C 이고 확률 < nli_sure
```

**문턱이 둘인 까닭** : 막을 실수는 거짓 지지 하나다. 지지에만 높은 문턱을 걸면 반대·무관 확정은 덜 잃는다. 문턱 하나면 반대까지 같이 보류돼 보류 ≤ 30% 를 넘기 쉽다.

**고르는 법 (`calibrate.py`, 새 dev · 온도 적용 뒤 확률)**

1. `nli_sure_support` : 0.50~0.99 · 0.01 간격에서 **dev 거짓 지지 ≤ dev 의 지지 아닌 쌍 수 × 2%** 를 만족하는 **가장 작은 값**. (game90 의 자 3/65 = 4.6% 보다 반쯤 낮춰 여유를 둔다. 지지 아닌 쌍이 120 이면 2쌍)
2. `nli_sure` : 같은 간격에서 **dev 확신 B·C 답 정확도 ≥ 0.90** 을 만족하는 가장 작은 값.
3. 두 값으로 dev 보류 비율을 잰다. 30% 를 넘으면 `nli_sure` 를 내려 맞추되 **`nli_sure_support` 는 안 내린다**(거짓 지지가 앞선다). 그래도 넘으면 그대로 두고 측정에서 판정받는다.

**설정 키** (AIMemoryTool `llm.toml`, 기본은 꺼짐)

```toml
nli_url = ""              # 예 "http://127.0.0.1:8092" · 비면 NLI 단을 건너뛴다
nli_timeout_ms = 1000     # 1~5000
nli_sure = 0.70           # 반대·무관 확정 문턱 · 0.34~0.99 · dev 로 고른 값으로 바꾼다
nli_sure_support = 0.90   # 지지 확정 문턱 · 0.34~0.99 · dev 로 고른 값으로 바꾼다
```

기본값은 「고른 값이 없을 때 안전한 쪽」이다. 실제 값은 prereg 의 값을 메인 PC 설정에 적는다. 문턱은 `model.json` 의 `scores` 에도 적어, 다른 툴이 같은 모델을 쓸 때 출발값으로 삼는다.

- **N1 이 멎거나 이상하면 그 자리에서 CPU 길(2순위)로 바꾼다.** 스크립트는 `--device cpu` 하나만 다르다.

## 사용자에게 물을 것

1. **옛 Laya 자리 치우기** (지우기라 승인 몫) — 길 1 이 안 쓰는 것이다.
   - mem 저장소(비공개) 안 `judge-laya/` 통째 (`freeze.py` 는 JudgeModel 로 일반 꼴로 다시 쓴다)
   - 메인 PC `~/.aimemory/laya/laya-v1/` (실험 모델)
   - 미니PC `~/judge-laya/` 7.5GB 중 `exp-20261008` · `ft4` · `hf` · `laya2` (약 6.3GB). **`.venv` 는 길 1 이 끝날 때까지 남겨야 한다** — CPU 길 · 0단계 CPU · ONNX 내보내기가 이 venv 를 쓴다.
   - 권장 : 저장소 `judge-laya/` 는 N3 커밋 때 지우고, 미니PC·메인 PC 의 모델·자료는 길 1 측정이 끝난 뒤 한 번에 지운다.
2. **GitHub 저장소 `officina-judge-tool`** — mem 기록에는 「사용자가 10-08 에 지웠다」고 적혀 있다. 지금 있는지 확인이 필요하다. 없으면 측정 통과 뒤 첫 푸시 때 다시 만들어야 한다(밖으로 나가는 일이라 사용자 몫). 측정 전에는 스튜디오 안 보통 폴더로 둔다.
