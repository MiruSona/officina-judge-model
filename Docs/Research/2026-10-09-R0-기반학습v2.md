## 1. 설정

```
run/podman-train.sh -e TORCH_ROCM_AOTRITON_ENABLE_EXPERIMENTAL=0 -e HF_HUB_OFFLINE=1 --name base-2 \
  train/train_nli.py --device cuda --dtype bf16 --init hf/xlm-roberta-large \
  --train data/prep/klue-train.jsonl \
  --train-epoch data/prep/kornli-e{epoch}.jsonl --train-epoch data/prep/mnli-e{epoch}.jsonl \
  --train-epoch data/prep/snli-e{epoch}.jsonl \
  --dev data/prep/klue-dev.jsonl --out runs/base-2 \
  --epochs 2 --batch 32 --max-len 128 --lr 8e-6 --warmup 0.10 --seed 1
```

- 바퀴당 쌍 : KLUE 24,998 + KorNLI 50,000 + MNLI 50,000 + SNLI 25,000 = 149,998 · 전체 스텝 9,376 (바퀴당 4,688).
- 128 에서 잘린 쌍 : KorNLI e1 147 · e2 150 · MNLI e1 229 · e2 206 · KLUE · SNLI 0. 자료 `nc` 는 일곱 다 false.
- 환경 : 게임 서버 없음 · llama `agent` 내림 · 이미지 digest `sha256:384aa1fe…` · torch `2.14.0a0+rocm7.15` · transformers 5.15.0 · 스크립트 SHA `47fdb870…`.
- 맛보기(`base-2-probe`, 60 스텝, `--max-steps`) : 0.43초/스텝 · GTT 13.6GB · 검사점 저장 포함 스왑 +0 → batch 32 그대로 본 판.

- **영어 평가 셋** : R0 은 영어 dev 를 따로 두지 않았다. 이번에 `multinli_1.0.zip` 안 `multinli_1.0_dev_matched.jsonl`(SHA `9db14e02…`)을 풀어 라벨 `-` 185줄을 뺀 앞 2,000줄을 `data/prep/mnli-devm-eval2000.jsonl`(SHA `0fbdd879…`)로 만들었다. 학습 표본 e1 · e2 와 (전제|가설) 겹침 0. 라이선스는 학습 셋과 같다.
- `read_nli_jsonl` 은 이름에 dev 가 든 파일을 늘 거부했다(학습 입력을 막는 규칙인데 읽기 길이 하나라 평가도 막았다). 기본값은 그대로 두고 `train_only=False` 인자와 `data_prep.py eval-en` 명령을 더했다. NC 이름(xnli · anli)은 여전히 거부한다.

- **함정** : fp32 XLM-R large 는 2.24GB 라 protobuf 한도(2GB)를 넘는다. `torch.onnx.export` 가 가중치를 내보낼 폴더에 낱개 파일 172개(`onnx__MatMul_…` 등)로 흩뜨렸고, `model.onnx` 는 1.4MB 그래프뿐이라 `onnx_sha256` 이 가중치를 안 덮었다.
- 고침 : 임시 폴더로 내보낸 뒤 흩어졌으면 `model.onnx.data` 한 파일로 모으고, `model.json` 에 `onnx_data_file` · `onnx_data_sha256` 칸을 더했다. 2GB 아래 몸통(klue)은 예전처럼 `model.onnx` 하나이고 두 칸은 null 이다. 시험 3개를 더했다.
- 메인 PC `~/.judgemodel/models/nli-base-v2/` 로 scp(`torch/` 는 안 옮김) 뒤 `model.onnx` · `model.onnx.data` · `tokenizer.json` · `model.json` SHA 를 미니PC 와 대조 — 같음.

| 검사 | 셋 | 결과 |
| --- | --- | --- |
| 일치 (`check_onnx.py --ref`) | K 48 + dev 204 = 252 | 토큰 불일치 **0** · 확률 차 최대 **9.7e-6** · 최고 답 **252/252** · 통과 |
| p95 (`--url`, 8093, 4 스레드, 순차) | 같은 252 | p50 136ms · **p95 493ms** · 최대 622ms · 통과 (자 1,000ms) |

klue 판 `nli-studio-v1` 이 같은 셋에서 p95 472ms 였다. 몸통이 커져도 셈 양은 비슷해 느려지지 않았다. 서버는 잰 뒤 내렸다. int8 은 안 만들었다.
