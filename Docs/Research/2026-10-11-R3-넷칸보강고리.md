## 결론

**넷 칸 보강 고리를 접는다(10-11 04:27).** 6바퀴를 돌았지만 dev 관문 11개를 다 넘은 판이 하나도 없다. **blind v4(220쌍)는 쓰지 않았다.**

**권장** : 넷 칸은 접되 코드(4칸 학습 · 서빙 · AIMemoryTool 손님)는 그대로 둔다. 8092 는 `nli-studio-v2`(3칸) 그대로다. 다시 열려면 아래 「다시 열 때」 셋 중 하나가 먼저 있어야 한다.

## 1. 진단 (소단계 19) — 옛 모델 견줌은 무효였다

R2 는 「옛 3칸 모델이 정답 a·b·c 에서 0.923, 넷 칸이 0.850 → d 를 배우며 a↔b 가 흐려졌다」고 적었다. 이 견줌은 기울어 있었다.

| 무엇 | 값 |
| --- | --- |
| blind v3 350쌍 중 옛 모델(r1-04) 학습 입력과 근거·주장·라벨까지 같은 쌍 | **181 (52%)** |
| 그 안의 a·b·c 167쌍을 옛 모델이 맞힌 수 | 164 (외운 것) |
| 옛 모델이 못 본 169쌍에서 a↔b 틀림 (a→b · b→a) | r2-02 3 · 5 / 옛 4 · 5 — **흐림 없음** |
| 못 본 169쌍에서 확신 거짓 지지 | r2-02 **1** / 옛 4 |
| r2-02 가 a·b·c 에서 지는 곳 | a·b 가 d 로 샘 (a→d 9 · b→d 6) |

- 그래서 고리는 「a·b ↔ d 경계」와 「긴 주장 속에 묻힌 flip」을 겨눴다. 자세한 표는 보강 설계 1절.

## 4. 합성 자료 검수에서 나온 것

R2 · R4 합성은 Opus 판정자 둘이 따로 라벨을 붙이고, 이미 확정된 실물 쌍을 함정으로 섞어 판정자를 검사했다.

| | R2 묻힌 flip | R4 a/d 경계 |
| --- | --- | --- |
| 만든 수 → 남긴 수 | 200짝 → 160짝 (320줄) | 110짝 → 109줄 (a 80 · d 29) |
| 판정자 함정 맞힘 | 16~18 / 20 | 15~17 / 20 (첫 B 판은 80% 아래라 버리고 다시) |
| κ (네 칸, 합성만) | 1.000 | 0.954 |
| 학습에 넣은 결과 | 277.5 (바퀴 2) | 279.5 (바퀴 3) |

- **R4 검수에서 함정 7개를 판정자 셋이 모두 같은 다른 라벨로 틀렸다.** 판정자가 아니라 함정 쪽, 곧 **train-r2 실물 쌍의 라벨이 흔들린다**고 본다. train-r2 라벨 재검토 후보다(목록은 git 밖 `synth-r4/README.txt`).
- R2 의 κ 1.000 은 이 꼴이 Opus 에게 쉽다는 뜻이기도 하다. 「4.3 에서 0.7 로 늘었다」 같은 말 안 되는 뒤집기가 걸러지지 않고 남았다. 모델이 뜻 없는 말투로 b 를 배웠을 수 있다(짐작).
- blind v4 의 3기억 짝 하나가 금지 목록 밖 train 기억을 써서 R2 출처와 1짝 겹쳤다. 그 짝은 합성에서 뺐다. 금지 목록은 blind 파일 본문에서 기억 id 를 직접 뽑아야 한다.

## 5. 측정 해석에 붙일 단서 — 꼬리표 떼기

- JudgeModel 학습 · 측정(`run_measure.py` · `run_fold.py`)은 기억 줄 머리 꼬리표(`왜 :` 따위)를 떼고 모델에 보낸다.
- 그런데 AIMemoryTool 손님(실제 `mem` 이 서버에 묻는 쪽)은 **10-11 전까지 원문 그대로 보냈다.** 리뷰에서 찾아 10-11 에 같은 규칙으로 떼게 고쳤다(미커밋).
- 그래서 **10-11 전의 blind v3 · fold40 숫자는 「뗀 글」로 잰 값이고, 실제 서빙(원문)과 다르다.** 꼬리표가 붙은 쌍은 blind v3 100/350 · dev-r2 91/344 다.
- 이번 고리의 dev-r2 숫자도 뗀 글로 쟀다. 손님을 고친 뒤로는 서빙과 같은 꼴이다.
