# v1.2 여섯 판이 같은 꼴로 깨지는 까닭 — 반복 실패 원인 조사 (2026-10-15)

- 왜 이 문서를 쓰나 : 사용자가 「같은 실수를 자꾸 반복하고 모델도 도돌이표가 되는 것 같다. 원인부터 조사하고 대책을 세우자」고 했다. 그래서 다음 판(K5 등)을 설계하기 전에, **판 하나의 원인이 아니라 여섯 판(B · K · K2 · K2-h · K3 · K4)에 걸쳐 되풀이되는 원인**을 본다.
- 쓴 사람 : Opus 서브에이전트 · 읽기와 셈만 했다(코드 · 셋 · 모델 · 미니PC 는 안 건드렸다. blind-g4 는 안 열었다).
- 칸 : a 지지 · b 반대 · c 무관 · d 비슷한 계열. 뜻은 `../Guide/라벨기준support-v6.md`.
- 표시 : **[원문]** = 다른 문서에 적힌 숫자 · 말 그대로 · **[셈]** = 원문 숫자로 이 문서가 다시 셈한 값 · **[추론]** = 이 문서가 엮은 말. 판의 줄임말(B4 · B4h · K …)과 R1~R8 은 `2026-10-14-v1판별원인비교.md`(이하 「원인 비교」)를 따른다.
- 숫자의 오름 · 내림 방향은 각 판 결과 문서 원문에서 옮겼다.

## 0. 결론 요약

1. **여섯 판 중 다섯은 「진짜 무너짐」 하나씩을 냈고, K4 만 「문턱 근처 깨짐」 하나뿐이다.** B4h c −.083 · K c −.044 · K2 d −.146 · K2-h d −.127 · K3 en b −.209 는 평균부터 크게 내렸다. K4 의 b@ko −.019 [−.0394, .0000] 는 평균이 작고 구간 위끝이 0 에 닿는다(2 · 5절). **K4 는 도돌이표가 아니라 「R1 을 고친 첫 판」이다** [원문 숫자 · 추론].
2. **무너짐 다섯 중 넷(B4h · K · K2 · K3)은 학습 전에 자료 통계만으로 미리 알 수 있었다.** 원천 × 칸 빈칸(R1)과 원천 × 칸 겹침 치우침(K2)은 얼린 학습 파일을 세면 나오는 값이다. 실제로 원인 비교는 그것을 **학습 뒤에** 셌다(3절).
3. **같은 교훈을 판마다 다시 배웠다.** B(10-13)에서 「VitaminC 를 a · b 로만 넣으니 c 가 b 로 감」이 이미 나왔는데, K3(10-14)는 VitaminC 를 d 로만 넣었다. R1 이 「원천 하나 = 칸 하나」라는 일반 규칙으로 적힌 것은 K3 가 깨진 **뒤**다. 교훈이 「그 판의 그 칸」으로만 적히고 다음 설계의 점검표가 되지 않았다(4절 ④층).
4. **판마다 목표가 「앞 판이 깬 칸 메우기」로 바뀌었다.** 10-12 에 정한 v1.2 목표는 실사용 mem 쌍의 b(잣대 3쌍 b 확률 .50 위)였다. 그 뒤 목표는 dev b(VitaminC 중심) → ko b → c@ko → d → c@ko 로 옮겼고, 잣대 3쌍은 K 판 뒤로 결과표에서 빠졌다(4절).
5. **K3 · K4 의 b@ko 깨짐은 한 판만 보면 잡음과 못 가른다.** McNemar 12 · 5(p .143), 구간 위끝 0. 다만 K2 → K3 → K4 세 판이 **같은 두 원천(klue-mrc · klue-answered) b 에서 같은 쪽으로** 내렸다. 세 판 모두 그 원천에 c · d 줄만 더했다. 작은 진짜 효과일 가능성이 높다고 본다 [추론, 5절].
6. **절차가 가장 큰 뿌리다.** 한 판에 사람 손 2~4시간 + 학습 2시간이 들고, 「미리 정한 대체 판」(B4h · K2-h)은 실제 깨진 까닭과 상관없이 돌았다. 사후 가설(K3 기제 신뢰 70% · K4 klue 「어림, 재지 않았다」)은 다음 판 전에 반증해 보지 않고 다음 판 설계의 전제가 됐다(4절).
7. **추천 대책 셋** (6절, 결정은 사용자) : ① 같은 자리가 두 번 깨지면 학습 판을 멈추고 이미 있는 pred.jsonl 로 진단부터(약 30분) ② 학습 전 자료 점검표를 「빈칸」에서 「원천별 칸 비율 이동 · 겹침 치우침 · 작은 칸 표본 수」로 넓혀 통과해야 학습을 띄움(도구 약 1시간 + 판마다 5분) ③ 다음 판 전에 목표 다시 확인 — K 또는 K4 를 use1 실사용 셋으로 한 번 재 보고 v1.2 가 실사용에 필요한지 사용자가 정함(약 1시간).

**정리** : 여섯 판 중 다섯(B4h · K · K2 · K2-h · K3)은 학습 전 셈으로 내다볼 수 있었고, K4 도 비율 이동은 셀 수 있었다. **빠진 것은 계산 능력이 아니라 「학습을 띄우기 전에 반드시 세는 차례」다** [추론]. 원인 비교 문서는 [셈] 열을 학습 **뒤** 얼린 층 파일에서 뽑았다 — 같은 파일이 학습 **전**에도 있었다.

### 5-2. 쉽게 풀면

- **붓스트랩 구간** : 같은 284쌍에서 묶음을 뽑기를 1만 번 되풀이해 「차이가 이 범위 안에 있을 것」을 본 것이다. [−.0394, .0000] 은 「아마 −3.9%p 에서 0 사이」라는 뜻이다.
- **위끝이 0 에 닿는다** = 「실제로는 안 바뀌었다」도 아슬아슬하게 이 범위 안이다. **나빠졌다고 증명된 것은 아니다.**
- **지킴 자는 반대를 묻는다** : 「−3%p 보다 크게 나빠지지 않았다고 말할 수 있나」. 아래끝이 −.0394 라 **그렇게 말할 수 없다.** 그래서 「깨짐」이다. 곧 깨짐 = 「지켰다는 증명을 못 함」이지 「나빠짐이 증명됨」이 아니다.
- **쌍 단위 검정**(McNemar)도 12 대 5 로 p .143 — 우연과 못 가르는 크기다 [원문].
- **이 자가 얼마나 빡빡한가** [셈 · 추론] : K 끼리의 짝 반폭 어림은 .0138(baseline-g4). 반폭이 .014 ~ .020 이면 평균 차가 대략 −.010 ~ −.016 보다 더 내리기만 해도 아래끝이 −.03 을 넘는다. K4 는 씨앗 sd 가 K 의 두 배(.0225)라 구간이 넓어져 더 쉽게 걸렸다.
- **작은 칸 하나가 다 끌었다** : klue 두 원천 39쌍에서 약 5.8쌍이 빠져 −.020 이 거의 다 설명된다(K4 문서 4절 [원문]). klue-mrc 19쌍에선 한 쌍이 .053 이다.

### 5-3. 그래서 진짜인가

- **한 판만 보면** 잡음 범위와 못 가른다(위끝 0 · p .143).
- **여러 판을 같이 보면** 진짜일 쪽에 무게가 실린다 [추론] : klue-answered b 가 K2 · K3 · K4 에서 .78 → .70 → .64 → .64 로 같은 쪽으로 내렸고, 세 판 모두 그 원천에 c · d 줄만 더했다(3절). 기제(같은 원천 안 칸 비율 이동)도 있다.
- **덜 믿을 까닭도 있다** [추론] : 네 판이 같은 39쌍 dev 를 쓴다. K 가 이 39쌍에서 우연히 높았다면(.842 · .780) 어느 판이든 내려 보인다. 서로 독립된 증거 셋이 아니다.
- **확인할 방법** : klue b 오판이 a 로 갔나 d 로 갔나(K4 문서 7절 「안 뽑음」)를 이미 있는 pred.jsonl 에서 뽑는다. d 로 갔다면 R2(d 를 더해 b 를 쓸어감)가 맞다. 학습 없이 된다.
