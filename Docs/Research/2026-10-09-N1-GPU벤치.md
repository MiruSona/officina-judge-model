# N1 GPU 벤치 (2026-10-09)

- 쓴 사람 : Opus 서브에이전트 · 소단계 N1 (설계 `JudgeModel/Docs/Design/2026-10-09-길1한국어NLI분류기설계.md` 9절)
- 무엇 : 무작위 초기화 roberta-large(klue 크기 336.7M) 학습 20 스텝 · batch 16 · seq 128 을 미니PC GPU(podman 이미지 `docker.io/kyuz0/amd-strix-halo-comfyui:latest`)에서 네 판 순차로 돌렸다.
- 코드 : `JudgeModel/train/bench.py` · 감싸개 `JudgeModel/run/podman-train.sh`

## 결론 먼저

| 판정 | 결과 | 근거 |
| --- | --- | --- |
| GPU 길을 쓸 수 있나 | **쓸 수 있다** | 네 판 다 정상 끝(stop_reason done) · 손실 유한 · GPU 멎음 없음 |
| bf16 을 쓸 수 있나 | **쓴다** (설계 3-2 자 통과) | bf16 첫 손실 1.08423 · fp32 1.08200 → **+0.21%** (자 ±5%) |
| KorNLI 표본 크기 | **바퀴마다 5만** (2 바퀴 10만, 번역체 67%) | bf16 **분당 2,476쌍** ≥ 1,500 (설계 2-2 갈림) |
| AOTriton 변수 | **끈다(0)** — 차이 없음 | 켬·끔 처리량 차 0.1% 안 · 손실이 비트까지 같다 |

- bf16 은 fp32 의 **3.1배**, CPU(16스레드)의 **11.6배**다. 기계 조사의 어림(bf16 10~18배 · fp32 4배)과 맞는다.
- 기반 학습 1 바퀴(KLUE 25k + KorNLI 5만 = 7.5만 쌍)는 seq 128 꽉 채운 셈으로 **약 30분**, 2 바퀴 1시간. KorNLI 10만이면 바퀴당 약 50분 [어림 : 벤치 처리량 그대로 나눔, 평가·저장 시간 뺌].
- 함정 둘을 밟았다 (아래 4절) : 이미지 profile 이 AOTriton 을 늘 켜 둔다 · GPU 판마다 llama 쪽 메모리가 스왑으로 밀린다.

## 1. 판별 결과

환경 : 게임 서버 내려감 · llama `agent` 떠 있음(GTT 22.1GB) · torch `2.14.0a0+rocm7.15.0a20260721` · hip 7.15.0 · attention `sdpa` · 이미지 digest `sha256:384aa1fe…`.
스텝 초는 앞 2 스텝을 뺀 평균이다.

| 판 | dtype | AOTriton | 스텝 초 | **분당 쌍** | 첫 스텝 초 | 첫 손실 | 끝 손실 | 손실 유한 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| n1-fp32-off | fp32 | 0 | 1.200 | **800** | 1.75 | 1.08200 | 0.75404 | 예 |
| n1-fp32-on | fp32 | 1 | 1.204 | **797** | 1.81 | 1.08200 | 0.75404 | 예 |
| n1-bf16-on | bf16 | 1 | 0.388 | **2,476** | 1.06 | 1.08423 | 0.48273 | 예 |

- 같은 배치를 20번 되풀이하는 벤치라 손실이 내려가는 것은 외우기다. 끝 손실 차(0.48 vs 0.75)는 정밀도 차로 궤적이 갈린 것이고 자가 아니다. 진짜 판(N6)의 KLUE dev 2,000 스텝 검사가 무너짐을 본다.

## 3. 메모리

GTT 늘어난 몫 = 판 피크 − 시작(22,099MB, llama `agent` 몫). 가용·스왑은 호스트 `free` 값.

| 판 | torch 최대 할당 | torch 최대 예약 | GTT 늘어난 몫 | 가용 시작 → 최저 | 스왑 판 전 → 판 뒤 |
| --- | --- | --- | --- | --- | --- |
| n1-fp32-off | 7,329MB | 8,036MB | +8,340MB | 27.7 → 18.5GB | 77 → 77MB |
| n1-fp32-on | 7,329MB | 8,036MB | +8,340MB | 28.2 → 18.7GB | 77 → 299MB (+222) |
| n1-bf16-on | 6,750MB | 6,964MB | +7,269MB | 28.4 → 19.8GB | 299 → 425MB (+126) |
| n1-bf16-off | 6,750MB | 6,964MB | +7,269MB | 28.5 → 20.0GB | 425 → 615MB (+190) |

- 판마다 스왑 증가는 자(+256MB) 안이라 멈추지 않았다. 다만 **쌓였다** — 77 → 615MB. 늘어난 몫은 거의 다 llama-server 의 VmSwap(549MB)이다. 판이 GTT 7~8GB 를 잡는 순간 한 번에 밀리고, 판 안에서는 더 안 늘었다(5초 감시 줄).
- 판이 끝나면 GTT 는 22,095MB 로 돌아오고 가용도 28~29GB 로 돌아온다. 밀린 스왑은 돌아오지 않는다.
- 설계 batch 32 는 활성값이 두 배라 GTT 몫이 더 크다 — 벤치는 batch 16 만 쟀다. 32 의 몫은 N6 첫 판에서 잰다.

## 4. 밟은 함정

### 4-1. 이미지 profile 이 AOTriton 을 늘 켠다

이미지의 `/etc/profile.d/01-rocm-envs.sh` 가 `TORCH_ROCM_AOTRITON_ENABLE_EXPERIMENTAL=1` · `TORCH_BLAS_PREFER_HIPBLASLT=1` 을 export 한다. `bash -lc` 로 띄우면 이것이 `podman run -e` 값을 덮는다(기계 조사 2-1 의 「환경변수 `VIRTUAL_ENV` 뿐」은 이미지 Config 만 본 것).
감싸개는 `-e` 값을 로그인 셸 뒤에 `env KEY=VAL python …` 으로 다시 걸게 고쳤다. bench 결과의 `aotriton` 칸으로 실제 값을 확인했다.

### 4-2. AOTriton 이 차이를 안 낸다

켬·끔 손실이 비트까지 같다 — 두 판이 같은 attention 커널을 탔다는 뜻이다 [추정 : attention_mask 를 넘기면 flash 길이 안 붙는다 · seq 128 이라 attention 몫도 작다]. 진짜 학습도 패딩 마스크를 넘기므로 같을 것이다. 실험용 변수라 **끈 쪽(0)** 으로 정한다.

### 4-3. GPU 판이 llama 쪽을 스왑으로 민다

llama `agent` 가 떠 있는 채 GTT 를 7~8GB 더 잡으면 커널이 llama-server 의 쉬는 쪽 페이지를 스왑으로 민다. 판당 +126~222MB, 네 판에 +538MB. 긴 학습은 처음 잡을 때 한 번 밀리므로 판 안에서 안 늘 것으로 본다 [추정]. **게임 서버가 떠 있으면 이 증가가 「스왑이 늘기 시작하는 판」 규칙에 걸린다.** 게임 서버 공존은 이번에 안 쟀다.

### 4-4. 게임 서버 확인 줄이 자기 자신을 센다

`pgrep -f "$JUDGEMODEL_GAME_PROC"` 는 그 낱말을 품은 ssh 셸 명령 줄도 센다(첫 시험 판이 `game=1` 로 찍힘). 감싸개는 `pgrep -f "^[^ ]*$JUDGEMODEL_GAME_PROC"`(명령 줄 첫 낱말이 서버 실행 파일)로 고쳤다. 게임 서버 프로세스 이름은 `JUDGEMODEL_GAME_PROC` 환경 변수로 준다.

## 5. 감싸개 `run/podman-train.sh` 요약

- `run/podman-train.sh [-e KEY=VAL]... [--name NAME] <src 기준 스크립트> [인자...]` · 호스트 `~/judgetool` → 컨테이너 `/work` · 로그 `~/judgetool/logs/<NAME>.log` · 심장 박동 `logs/<NAME>.heartbeat`.
- 장치 · 보안 인자는 앞서 다른 툴 실측 때의 꼴(`--device /dev/kfd --device /dev/dri --group-add keep-groups --security-opt seccomp=unconfined --security-opt label=disable --ipc=host`).
- `--memory 20g --memory-swap 20g` (호스트 RAM 몫 · `JT_MEM_LIMIT`). GTT 는 cgroup 이 다 못 잡으니 감시가 상한 노릇.
- 5초마다 감시 : 심장 박동 60초 끊김(첫 박동 전 180초 유예) · 스왑 +256MB · 게임 서버 있을 때 가용 < 10GB · 게임 서버 새로 뜸. 걸리면 `podman kill`, 30초 안에 안 끝나면 `GPU_STUCK` 줄을 남기고 끝낸다(재부팅은 사람).
- 이번 네 판에서는 감시가 한 번도 안 걸렸다 — **멈춤 길 자체는 시험 안 했다.**
